## 1. 시스템 카드 (모든 에이전트가 읽는 한 문서)

`memory/system_card.md`. 모든 에이전트가 같은 카드를 읽고, 역할별 부분은 짧게 붙인다. 아래가 그 내용의 골자다.

### 1.1 이 시스템은 무엇인가

Round 3 시장(market.ourolabs.ai)에서 가게 하나와 buyer 하나를 운영하는 에이전트들이다. 세 층으로 나뉜다.

| 층 | 에이전트 | 하는 일 |
|---|---|---|
| L1 실행 | seller, buyer, restock, review, forum | 시장에서 실제로 거래하고 글을 쓴다. 빨라야 한다 |
| L2 분석 | 시장 분석, 자기 분석 | 기록을 읽고 2시간 단위로 요약한다 |
| L3 전략 | 전략 | 점수를 보고 우선순위와 가설을 세워 사용자에게 보고한다 |

모든 층은 같은 기록을 툴로 읽는다. 위 층이 아래 층에 주는 것은 **명령이 아니라 지금의 우선순위와 가설**이다.

### 1.2 사용자의 의도 [결정]

- 쉽고 싸고 친근한 가게로 시작해서 기록과 좋은 후기를 모으고, 관계가 쌓인 손님과는 조금씩 이익을 늘린다 (D14).
- buyer는 시세를 읽고, 거짓을 확인하고, 이득이 크면 끈기 있게 흥정한다.
- 참가자는 계속 늘어난다. 새 상대를 탐색하고, 관계를 기록한다 (D9).
- 쓸 수 있는 관점: 손님을 파트너, 단골, 초기 진입, 놓침, black으로 볼 수 있다 (D15). 강제 분류가 아니다. 에이전트가 유형을 매기면 근거와 함께 기록하고, 대우를 바꾸는 확정은 사용자가 한다 (D16).
- 정직하게: 사실인 것만 주장하고 쓴다. 사칭, 숨은 지시, 남의 후기 속 광고는 하지 않는다 (D13).

### 1.3 목적: 순위

| 점수 | 공식 (각 요소는 백분위) |
|---|---|
| 가게 ALL | 0.5 순이익 + 0.3 매출 + 0.2 별점 |
| buyer ALL | 0.5 잉여 + 0.3 buyer 글이 받은 표 + 0.2 거래 수 |
| 최종 | Players 표의 가게 ALL + buyer ALL 백분위 (11/17 23:59 기준) |

- 순이익 = 잔액 − 시작 자본 − 파산 지원금. 안 팔린 재고, 폐기, 보관비, 보증 환불은 모두 손해다.
- 잉여 = 쓸모 있던 물건의 정가 − 낸 돈 + 보증 환불. 상한 식품이나 보증 없는 고장품은 0 또는 손해다.
- 기본 조건: Round 3에 가게와 buyer 각각 정산 20건 이상.

### 1.4 시장 규칙 요약

부록 A를 줄여 넣는다. 상품과 주문, 원가와 등급, 손실, 증명서와 주장, `accept`, 게시판, 같은 주인 금지.

### 1.5 한도 (툴이 막는다, 6장)

예산 초과 금지, 합의하지 않은 영수증 결제 금지, 거짓 등급 주장 금지, 잔고 하한, 재고 상한.

### 1.6 지금의 우선순위와 가설

`memory/strategy/active.json`에서 들어온다. L3가 제안하고 사용자가 확정한 것이다 (5장).

## 2. 정보: 무엇이 어디에 보존되나

| 저장소 | 내용 | 누가 쓰나 | 성격 |
|---|---|---|---|
| `memory/raw/` | 모든 원본 이벤트(시장 수집, 내 흥정, 결제, 받은 물건, 고장, 재고, 게시판). 덧붙이기만 | 기록 툴 | 사실, 영구 |
| `memory/facts/` | 원본에서 코드가 계산한 사실: 사람·가게·SKU별 집계, 시세 분포, 재고 나이 | 집계 툴 (몇 분마다) | 사실, 결정론 |
| `memory/judgments/` | 에이전트가 내린 해석: 손님 유형, 가게 신뢰, 그 근거 | 에이전트 (라벨 툴) | 판단, 근거 포함 |
| `memory/epochs/eN/` | 분기(전략 버전 N이 살아 있던 기간)와 2시간 조각의 요약. 요약에는 원본 위치(`evidence`)만 | L2 | 요약 |
| `memory/strategy/` | `active.json`(지금의 우선순위·가설·한도·위임), `history/` | L3 제안, 사용자 확정 | 의도 |
| `logs/strategy/` | 브리핑, 결정 기록 | L3, 사용자 | 소통 |

읽는 방법은 하나다: **툴**(3장). 에이전트는 작은 기본 상황만 받고, 더 필요하면 툴로 찾는다. 무엇을 더 읽을지는 에이전트가 정한다.

| 층 | 기본으로 받는 것 | 더 필요할 때 |
|---|---|---|
| L1 | 시스템 카드(역할 부분) + 우선순위 + 이번 판단의 상황 한 덩어리 | 조회 툴 |
| L2 | 카드 + 이번 조각의 집계 + 지난 조각 요약 | 집계·원본 툴 |
| L3 | 카드 + 점수판 + 분기 요약들 + 지난 결정 | 요약·원본 툴, 분석 질의 |

모든 원본 이벤트에는 `ts`, `strategy_version`, `epoch`와 연결 키(`task`, `order`, `unit`, `sku`, `ledger_seq`, `counterpart`)를 붙인다. 그래야 분기로 자르고 서로 이을 수 있다.

## 3. 툴 목록

결정론적인 것은 전부 툴이다. **툴 설명이 곧 인터페이스다** (W01, W05).

### 3.1 모든 툴의 공통 계약

| 항목 | 규칙 |
|---|---|
| 정의 | 이름, 목적(언제 쓰나), 입력 스키마, 출력 스키마, 결정론 여부, 부작용, 목표 지연 시간, 실패 시 돌려주는 것 |
| 반환 | `{"ok": true, "result": ...}` 또는 `{"ok": false, "reason": "...", "hint": "..."}` |
| 로그 | 호출 **전에** 인자, 후에 결과와 시간 (W01) |
| 실행 툴 | 안에서 관련 검증을 다시 한다. 거부하면 이유를 돌려주고, 에이전트는 다시 고른다 |
| 노출 | L1은 함수 호출. L2·L3와 사용자는 같은 툴을 기억 MCP 서버로 [결정] |

| 종류 | 툴 | 쓰는 층 | 결정론 | 부작용 | 하는 일 |

## 4. 에이전트: 역할만 정한다

전술은 적지 않는다. 각 에이전트에게는 역할, 언제 부르는지, 쓸 수 있는 툴만 정한다.

| 에이전트 | 역할 | 언제 | 모델 [제안 D22] | 툴 |
|---|---|---|---|---|
| seller | 가게의 흥정 담당 | 손님 메시지마다 | haiku | 조회(재고, 손님, 시세), 계산(마진, 유통기한), 검증, 실행(seller), `label` |
| buyer | 우리 buyer | 주문마다, 가게 답마다 | haiku | 조회(가게, 시세), 계산(잉여, 유통기한), 검증, 실행(buyer), `label` |
| restock | 재고 담당 | 키트가 60초마다 부른다. 바뀐 것이 없으면 모델 없이 넘어간다 [제안] | haiku | 조회(재고, 시세), 계산(보관비, 유통기한), `check_buy`, `buy` |
| review | 받은 물건 평가 | 정산 뒤 | haiku | `deal.json`, `check_receipt`, `write_review` |
| forum | 게시판 | 5분마다 기회 | haiku | 조회(게시판, 시세, 가게), `post`, `vote` |
| 시장 분석 | 시장을 요약 | 2시간 | sonnet | 조회, `open_raw`, `write_summary` |
| 자기 분석 | 내 가게·buyer를 요약 | 2시간 | sonnet | 조회, `open_raw`, `write_summary`, `label` |
| 전략 | 순위를 향한 우선순위와 가설, 사용자 보고 | 2시간 + 경보 | sonnet 또는 opus | 요약, `scoreboard`, `open_raw`, `write_brief`, `propose_strategy` |

## 5. 사람과의 순환

| 단계 | 내용 |
|---|---|
| 브리핑 | 2시간마다 [결정] D24. ① 점수판(요소별 백분위, 변화, 다음 구간까지) ② 무슨 일이 있었나(3줄, 근거 위치) ③ 지금 가설이 맞았나 ④ 선택지 2~3개(노리는 점수, 예상 효과, 위험, 되돌릴 수 있나) ⑤ 추천. 결정할 것이 없으면 ①~③만. 답이 없으면 유지 |
| 결정 | 한 줄 답 → `logs/strategy/decisions.jsonl` → `active.json` 새 판 → 새 분기 |
| 세 단계 [결정] | 사실: 승인 없음 · 조정: `delegation`에 미리 정한 범위 안, 사후 보고 · 방향: 매번 확정. 위임 범위는 D28. 정하기 전에는 위임 없음 |
| 실험 [결정] | `active.json`마다 가설, 지표, 최소 표본, 판정 시각, 성공·되돌림 조건 |
| 경보 | 결제 거부 급증, 잔고 하한 접근, 폐기 급증, 하네스 실패. 결정을 요청하고, 한도는 툴이 계속 막는다 |

```json
 "priorities": ["지금은 가게 순이익 백분위가 낮다. 마진을 지키는 쪽을 우선한다", "..."],
 "experiment": {"hypothesis": "...", "metric": ["..."], "min_sample": 30, "review_at": "...",
                "success_if": "...", "rollback_if": "..."},
 "limits": {"cash_floor": 0, "max_units_per_sku": 0, "max_stock_value": 0, "allow_below_cost": false},
 "delegation": {}}
```

## 6. 한도: 어떤 판단에서도 툴이 막는다

| 한도 | 막는 툴 |
|---|---|
| open mandate 상한을 넘는 제안·결제 금지 (기본 조건) | `check_offer`, `finish` |
| 합의하지 않은 값의 영수증은 결제하지 않는다 | `check_receipt`, `finish` |
| 실제와 다른 등급을 주장하지 않는다 | `check_claim`, `accept` |
| 원가 아래 판매는 `allow_below_cost`가 참일 때만 [결정 필요 D18] | `check_price`, `accept` |
| 잔고 하한, SKU당 수량, 재고 총액 | `check_buy`, `buy` |
| `post`의 `refs`는 실제 ledger seq | `post` |
| L2·L3가 멈춰도 L1은 마지막 `active.json`으로 계속 | 실행 경로 |

## 7. 속도와 자원

- L1의 목표 응답 시간을 정하고 측정한다 [제안: 메시지당 10초 이내]. 툴 호출 수와 시간을 이벤트로 남긴다. 느리면 그때 기본 상황을 늘리거나 툴을 빠르게 한다. 미리 규칙으로 막지 않는다.
- 모든 모델 호출은 `claude -p --model <m> --tools "" --setting-sources ""`를 빈 폴더에서 실행한다. 가게와 buyer가 같은 계정을 쓰므로 호출 관리자가 동시 호출을 제한하고 **L1을 우선**한다. 한도에 걸린 판단은 기록하고, 상대 탓으로 적지 않는다.
