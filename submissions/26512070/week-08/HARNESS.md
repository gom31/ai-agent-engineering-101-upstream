## 0. 평가 기준과 자체 평가표

중간 평가 기준(week-08 HW)을 이 설계의 채점표로 쓴다. 기준선은 **키트 기본형**이다. starter `seller_r3.py`(메시지마다 harness 한 번, 원가 아래 금지, 유통기한 빠른 유닛, 품질·보증 없음), `default_restock()`(재고 20개 아래면 무작위 SKU), 기억·훅·게시판 없음.

| 기준 (비중) | 보는 것 | 기본형 | 이 설계 | 증거 | 자체 평가 |
|---|---|---|---|---|---|
| 1a 모델 (40% 안) | 어떤 모델을 어디에 | haiku 하나 | 층마다 다른 모델: 실행은 빠르게, 분석·전략은 무겁게 (7장) | REPORT (1), `[model]` 로그 | 설계됨 |
| 1b 컨텍스트 | 지난 거래와 평판을 다음 결정에 어떻게 넣나 | 대화 기록만 | 분기·시간 조각 요약 → 전략 → 실행용 플레이북으로 압축. 실행은 최신 전략만 (5·6장) | `memory/` 구조, 프롬프트 로그 | 설계됨 |
| 1c 툴 | 무엇을 툴로, 어떻게 | 없음 | 층마다 다른 툴. 실행은 조회 몇 개, 분석은 집계와 원본 열람, 전략은 분석 질의 (8장) | 코드, 툴 로그 | 설계됨 |
| 2 구조 독창성 (30%) | 기본형과 어떻게 다른가 | 메시지 단위 단일 루프 | 실행 ← 전략 ← 분석 ← 기록의 **바깥 제어 순환**과 사람 검토 (1장 그림) | `architecture.tex/.pdf` | 설계됨 |
| 3 순위 (30%) | Players 백분위 | – | 전략 에이전트의 목표 함수가 곧 순위 공식 (2장) | board, REPORT (3) | 운영 중 |
| 기본 조건 | 가게·buyer 정산 각 20건 | – | 입장 뒤 3일 안 | 정산 줄 | 운영 중 |

자체 평가는 구현 단계마다 `설계 전 / 설계됨 / 구현됨 / 증거 있음`으로 갱신한다.

## 1. 설계 방식: 바깥에서 안으로

목표(점수)에서 거꾸로 각 층의 요건을 정한다.

| 층 | 묻는 것 | 요건이 되는 것 |
|---|---|---|
| **L3 전략** | 사용자에게 어떤 정보와 전략을 줘야 결정하기 쉬운가? 그게 점수 기준에 맞는가? | 2장 |
| **L2 분석** | seller와 buyer의 어떤 정보가 있어야 전략 에이전트가 명확히 판단하나? | 3장 |
| **L1 실행** | seller와 buyer는 어떤 구조여야 상황에 맞게 바뀌고 바르게 판단하나? 컨텍스트와 메모리는? | 4장 |

```
                         사용자
                     ▲ 브리핑   │ 결정
                     │         ▼
   ┌──────────── L3 전략 에이전트 (목표 = 순위) ─────────────┐
   │ 점수판 읽기 · 선택지 만들기 · 결정을 전략 vN으로 컴파일       │
   └───────▲─────────────────────────────┬──────────────────┘
           │ 분기·조각 요약                  │ 전략 vN (플레이북) + 새 분기 시작
   ┌───────┴────────┐  ┌─────────────────┐  │
   │ L2 시장 분석     │  │ L2 자기 분석      │  │
   │ ledger·게시판·   │  │ 내 seller·buyer  │  │
   │ 남의 재고·후기    │  │ 이벤트·점수 요소   │  │
   └───────▲────────┘  └───────▲─────────┘  │
           │ 원본 (필요할 때만)      │ 원본         ▼
   ┌───────┴──────────────────────┴───────────────────────────┐
   │ 기록 층 (코드): raw/ 덧붙이기만, 모든 이벤트에 전략 버전 표시   │
   └───────▲──────────────────────────────────▲───────────────┘
           │ 시장 수집                          │ 실행 이벤트
   ┌───────┴─────────┐        ┌───────────────┴───────────────────┐
   │ 시장 (키트 v4)    │◀──────▶│ L1 실행: seller · buyer · restock    │
   └─────────────────┘        │ review · 게시판. 플레이북만 읽고 판단   │
                              └───────────────────────────────────┘
```

핵심 규칙: **L1은 최신 전략(플레이북) 하나와 이번 판단의 사실만 본다.** 역사와 분석은 L2와 L3가 맡는다.

## 2. L3 전략 에이전트: 사용자에게 무엇을 주나

### 2.1 목표 함수 = 순위 공식

| 점수 | 공식 (각각 백분위) | 전략 에이전트가 보는 지렛대 |
|---|---|---|
| 가게 ALL | 0.5 순이익 + 0.3 매출 + 0.2 별점 | 마진 × 수량 − (폐기 + 보관비 + 보증 환불 + 안 팔린 재고) · 수량 · 후기 |
| buyer ALL | 0.5 잉여 + 0.3 buyer 글 표 + 0.2 거래 수 | (정가 − 낸 돈) − 상한 식품·고장 손실 · 쓸모 있는 글 · 거래 수 |
| Players | 가게 ALL + buyer ALL | 둘 중 **백분위를 올리기 쉬운 쪽**에 노력을 배분 |

백분위라서 절대값보다 **남들과의 위치**가 중요하다. 그래서 브리핑은 늘 "다음 구간까지 얼마 남았나"를 보여 준다.

### 2.2 브리핑 (사용자가 읽는 것)

`logs/strategy/brief-<시각>.md`. 한 화면 안에 읽히게, 결정은 한 줄로 답하게 만든다.

| 칸 | 내용 |
|---|---|
| ① 점수판 | Players 백분위, 가게·buyer ALL과 6개 요소 각각의 백분위, 지난 브리핑 대비 변화, 다음 구간까지의 거리 |
| ② 무슨 일이 있었나 | 3줄 이내. 각 줄에 근거 요약의 위치 |
| ③ 지금 전략이 통했나 | 이번 분기와 지난 분기의 같은 지표 비교. 표본 수와 함께 |
| ④ 선택지 2~3개 | 각각: 어느 점수 요소를 노리나 · 예상 효과 · 비용과 위험 · 플레이북에서 무엇이 바뀌나 · 되돌릴 수 있나 |
| ⑤ 결정 요청 | 추천 하나와 이유. 답이 없을 때의 기본값은 "지금 전략 유지" |
| ⑥ 부록 | 데이터 신선도, 이상 징후, 열린 질문 |

### 2.3 결정의 흐름

```
사용자 답 (예: "B, 단 식품은 빼고")
 → logs/strategy/decisions.jsonl 에 기록 (누가, 언제, 무엇을, 왜)
 → 전략 에이전트가 플레이북 vN+1 작성 → 코드 검사 (스키마, 코드 한도와 충돌 없는지)
 → memory/strategy/active.json 교체 (원자적 쓰기), 이전 판은 history/에
 → 새 분기 e(N+1) 시작
```

- 플레이북은 **사용자가 확정한 것만** 들어간다 (방향 P10).
- 급한 경우(예: 결제 거부 급증, 잔고 하한 접근)에는 브리핑을 기다리지 않고 경보를 낸다. 경보도 자동 반영하지 않고 결정을 요청한다. 단, 코드 한도(9장)는 그와 무관하게 항상 막는다.

### 2.4 주기 [결정] D24 (2026-11-03)

정기 브리핑 **2시간마다** + 경보. 분석 조각(5장 M2)도 2시간 단위로 맞물린다. 2주 동안 약 170번이므로, 결정할 것이 없는 회차는 ①~③만 담은 짧은 상태 보고로 끝내고 ④⑤는 비운다. 답이 없으면 지금 전략을 유지한다.

## 3. L2 분석 에이전트: 전략 에이전트가 판단하려면 무엇이 필요한가

두 분석 에이전트 모두 **코드가 먼저 원본을 집계**하고, 모델은 집계와 소수의 표본만 읽는다. 결과는 고정된 모양의 요약으로 남긴다.

### 3.1 시장 분석

| 질문 | 지표 (조각마다) | 원본 |
|---|---|---|
| 무엇이 팔리나 | 카테고리·SKU별 정산 수, 속도, 가격 분포(가능하면) | ledger `settle` [확인: 가격 필드] |
| 누가 무엇을 사나 | buyer별 카테고리 분포 (숨은 선호 찾기) | ledger |
| 경쟁은 | 가게별 재고·카테고리, 후기 평균, 정산 수 | `/api/shops` 재고 [확인], 후기 |
| 신뢰 | 등급 주장 거짓 비율, 고장 많은 상품, 사칭·조작 글 | ledger, 게시판 |
| 게시판 | 표를 많이 받는 글의 종류, 활발한 주제, "구합니다" 글 뒤의 거래 | `forum.json` |
| 순위 지형 | 요소별 백분위 경계값 (다음 구간까지의 거리) | board |

### 3.2 자기 분석

| 질문 | 지표 (조각마다, 분기별 비교) | 원본 |
|---|---|---|
| 점수 요소 | 순이익, 매출, 별점 / 잉여, 글 표, 거래 수 | 기록 층, board |
| 가게 흐름 | 방문 → 흥정 → 합의 → 정산, 단계별 이탈과 사유 | seller 이벤트, 키트 로그 |
| 재고 건강 | 재고 나이, 곧 상할 식품, 보관비, 품절로 놓친 요청, 폐기 손실 | `inventory.json` 이력, restock 이벤트 |
| 손님 | 손님별 요약과 유형 후보(파트너, 단골, 초기 진입, 놓침, black) | seller 이벤트 + ledger |
| buyer 흐름 | 주문 → 고르기 → 흥정 → 결제/거부(사유) → 받은 물건 → 고장 | buyer 이벤트, `payments.jsonl`, `deal.json`, `broken.jsonl` |
| 거래처 | 가게별 정직성, 주장 참·거짓, 고장, 잉여 | 같음 |
| 판단 품질 | 응답 시간, 하네스 실패, guard 개입, 플레이북 준수율 | 실행 로그 |

### 3.3 요약의 모양 (조각 하나)

```json
{"epoch": "e3", "slice": "2026-11-05T12:00/18:00", "strategy_version": 3,
 "metrics": {"shop": {...}, "buyer": {...}},
 "notable": [{"what": "김치 카테고리 정산 2배", "evidence": [{"src": "ledger", "seq": [2100340, 2104410]}]}],
 "hypotheses": [{"claim": "...", "support": "...", "n": 37, "confidence": "low|mid|high"}],
 "questions_for_strategy": ["..."]}
```

`evidence`는 원본의 위치다. 전략 에이전트나 사용자가 필요할 때만 원본을 연다.

## 4. L1 실행: seller와 buyer의 시스템 요건

### 4.1 읽는 것: 느린 전략 + 빠른 사실 [결정] (2026-11-03)

L1이 읽는 것은 두 파일이다. 속도와 승인 방식이 다르다.

| 파일 | 내용 | 누가 바꾸나 | 주기 |
|---|---|---|---|
| `memory/strategy/active.json` | 방향 문장, 한도, 가설 (전략 vN) | L3가 제안, **사용자가 확정** | 브리핑 결정 때 (2시간마다 기회) |
| `memory/facts/live.json` | 사실 조회표: 가게 신뢰도, 손님 유형 후보, 가격대, 팔림새, 재고 경보 | **코드** (L2 집계), 승인 없음 | 몇 분마다 |

```json
// active.json — 느린 전략
{"version": 3, "epoch": "e3", "since": "...", "approved": "user 2026-11-05T09:10",
 "seller": {"directions": {"default": "...", "by_customer_type": {"단골": "...", "초기 진입": "..."}},
            "units": "...", "claims": "...", "warranty": "..."},
 "buyer": {"directions": {"pick": "...", "haggle": "..."}, "accept": {...}},
 "restock": {"envelope": {"...": "..."}},
 "forum": {"directions": "...", "topics": ["..."]},
 "limits": {"cash_floor": 0, "max_units_per_sku": 0}}

// live.json — 빠른 사실
{"updated": "...", "from_epoch": "e3",
 "shop_trust": {"<shop>": {"level": "honest|caution|blocked", "why": "...", "evidence": [...]}},
 "customer": {"<buyer>": {"type_candidate": "단골", "type_confirmed": null, "deals": 0, "last": "..."}},
 "price_band": {"<category>": [10, 50, 90]}, "sell_through": {"<category>": 0}}
```

- **방향 문장**은 사람이 정한 전략이다. 숫자 규칙이 아니라 방향이고, 폭은 모델이 판단한다 ([결정] D11).
- **사실**은 결정이 아니라 관찰이라 승인 없이 바로 반영한다. 속인 가게를 바로 `blocked`로 두는 것 같은 반사 행동이 여기서 나온다. 단, **손님 유형은 후보만 자동**이고 대우에 쓰는 것은 사용자가 확정한 `type_confirmed`다 ([결정] D16).
- 실행은 이번 상대·상품의 한 줄만 꺼내 쓴다. 역사 전체를 읽지 않는다.
- **한도(limits)**는 코드가 지킨다 (9장).

### 4.2 판단 경로 (빠르게)

```
요청 도착 → 코드: 플레이북에서 관련 줄만 꺼냄 (상대 유형, 상품 가격대, 유닛 원가·등급)
          → 모델 1회 (haiku, 작은 프롬프트) → validate → guard → 응답
          → 이벤트 기록 (전략 버전 포함)
```

- 프롬프트 크기 상한 [제안]: 방향 문장 + 표 몇 줄 + 대화로 2천 토큰 이내.
- 하네스가 늦거나 실패하면 코드 기본 행동(플레이북의 기본값)으로 응답하고 기록한다.
- 키트 기본형과의 차이: 같은 "메시지마다 모델 한 번"이지만, 상대·상품에 맞춘 방향과 사실이 들어가고, 그 방향이 바깥에서 바뀐다.

### 4.3 남기는 것: 분석이 쓸 수 있는 이벤트

모든 이벤트는 `raw/<원천>/<날짜>.jsonl`에 덧붙인다. **공통 필드**: `ts`, `strategy_version`, `epoch`, 연결 키(`task`, `order`, `unit`, `sku`, `ledger_seq`), `counterpart`(알면).

| 이벤트 | 추가 필드 |
|---|---|
| seller 메시지·결정 | 요청 문장, 고른 유닛(원가, 등급, 유통기한), 호가·제안, 결정, `thought`, 모델 시간, guard 개입 |
| seller 거래 종료 | 결과, 가격, 주장(claim), 보증, 증명서, 흥정 턴 수 |
| buyer 주문 | 카테고리, 예산, SKU 후보, 고른 가게와 이유, 정가 |
| buyer 거래 종료 | 합의가, 영수증, `accept`, 결제 결과·사유, 받은 물건(등급, 주장 참·거짓), 잉여 |
| restock | 산 SKU·수량·원가, 잔고 전후 |
| 손실 | 폐기, 보관비, 고장·환불 |
| 게시판 | 쓴 글, 표, 받은 표 |
| 하네스 | 호출 자리, 모델, 시간, 실패 |

## 5. 메모리: 분기와 시간 조각

```
memory/
  raw/                         원본, 덧붙이기만 (기록 층)
    market/ledger-<날짜>.jsonl   seller/ buyer/ restock/ forum/ inventory/
  epochs/
    e3/                        분기 = 전략 버전 3이 살아 있던 기간
      meta.json                시작·끝, 전략 버전, 원본 범위(ledger seq, 파일 줄)
      slices/2026-11-05T12.json   시간 조각 요약 (3.3의 모양)
      summary.json             분기 요약 (조각들을 접은 것, 분기가 끝나거나 갱신될 때)
  strategy/
    active.json                L1이 읽는 전략 (느림, 사용자 확정)
    history/v1.json ...        지난 전략
  facts/
    live.json                  L1이 읽는 사실 (빠름, 코드가 갱신)
  index.json                   분기·조각 목록과 원본 위치
```

| 규칙 | 내용 |
|---|---|
| M1 분기 | 전략이 바뀔 때마다 새 분기. 분기 사이 비교가 "그 전략이 통했나"의 근거 |
| M2 조각 | 분기 안을 **2시간**으로 자른다 (브리핑 주기 D24에 맞춤). 코드 집계와 `live.json` 갱신은 몇 분마다, 모델 요약은 조각마다 |
| M3 접기 | 조각 요약 → 분기 요약 → 전략 에이전트. 위로 갈수록 작아진다 |
| M4 원본은 필요할 때만 | 요약에는 원본 위치(`evidence`)만 둔다. 열람은 툴로(8장), 크기 제한을 둔다 |
| M5 L1의 기억 | L1은 플레이북과 이번 판단의 표 한 줄만. 그 외 기억은 L1에 없다 |
| M6 보존 | 원본은 지우지 않는다. 커밋 시점은 [결정 필요 D21] (공개 포크) |

## 6. 컨텍스트 예산 (층별)

| 층 | 한 번에 보는 것 | 상한 [제안] |
|---|---|---|
| L1 실행 | 방향 문장 + 표 몇 줄 + 대화 | 2천 토큰 |
| L2 분석 | 코드 집계 + 표본 몇 건 + 지난 조각 요약 | 1만 토큰 |
| L3 전략 | 분기 요약들 + 최신 조각 + 점수판 + 지난 결정 | 2만 토큰 |

남의 글(가게 메시지, 후기, 게시판)은 어느 층이든 데이터로 표시해서 넣는다 (방향 P8).

## 7. 모델 [제안, 결정 필요 D22]

| 층 | 빈도 | 모델 | 이유 |
|---|---|---|---|
| L1 실행 | 메시지·주문마다 | haiku | 수가 많고 응답 시간이 거래에 걸린다 |
| L2 분석 | 조각마다 | sonnet | 집계를 해석하고 가설을 세운다 |
| L3 전략 | 하루 2번 + 경보 | opus 또는 sonnet | 횟수가 적고 판단이 무겁다 |
| 기록·집계·한도 | 항상 | 코드 | 숫자와 규칙 |

모든 호출은 `claude -p --model <m> --tools "" --setting-sources ""`를 빈 폴더에서. 같은 계정을 나눠 쓰므로 **L1이 우선**이다. 호출 관리자가 동시 호출 수를 제한하고, L1이 밀리면 L2·L3를 미룬다.

## 8. 툴 (층별)

| 층 | 툴 | 규칙 |
|---|---|---|
| L1 | `customer(name)`, `price_band(category)`, `unit_info(unit)` — 플레이북 표 조회 | 플레이북에 있는 것만. 실행 전·후 로그 |
| L2 | `aggregate(source, slice, query)`, `open_raw(pointer, limit)`, `prev_slice()` | 원본은 위치와 크기 제한으로만 |
| L3 | `epoch_summary(e)`, `slice_summary(e, t)`, `scoreboard()`, `ask_analyst(question)`, `open_raw(pointer, limit)` | 필요할 때만 아래로 내려간다 |
| 최종 행동 | L1: 흥정·구매·글 행동 / L2: 요약 쓰기 / L3: 브리핑과 플레이북 초안 쓰기 | 모두 스키마 검사. 플레이북 반영은 사용자 확정 뒤 |

| 실패 | L2·L3가 멈춰도 L1은 마지막 플레이북으로 계속 돈다 |
